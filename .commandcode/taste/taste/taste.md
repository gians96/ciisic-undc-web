# Taste
- Before touching code, expects the agent to inspect the real project first: framework, existing components, styles, and the actual folder/asset structure — never assume paths or folder names (e.g. verify whether the folder is `merchandising` or `merchadising`). Confidence: 0.85
- Prefers surgical changes with explicit scope limits: do not touch other sections, navigation, or already-working flows not related to the request ("está perfecto, solo que cambia la imagen…"). Confidence: 0.85
- Frequently double-checks the scope of a change after it is delivered ("¿solo has movido eso, verdad? nada más?"), so proactively state exactly which file and which parts changed and confirm that the image, the other cards, and unrelated pages were left untouched. Confidence: 0.65
- Does not want new dependencies installed unless strictly necessary; if an icon library or helper already exists in the project, use that. Confidence: 0.75
- Before delivering, expects verification: run lint/tests, start the project, and check by HTTP that the page and every visible asset (each image) respond (200), plus confirm the layout works both on desktop and mobile (desktop/mobile breakpoints, no overflow). Also expects the project's available checks (lint, typecheck, build) to be executed and their results reported. Confidence: 0.8
- Final response should report which files were modified, the exact asset path used, and how to verify the change locally (commands + URL). Confidence: 0.8
- Prefers reusing existing components/structures and avoiding duplicated markup (e.g. a `v-for` over a data array) instead of copying a component or creating a parallel section. Confidence: 0.8
- Keep exact given file/asset names: never rename a file or substitute the provided image for another. Confidence: 0.7
- Never invent data: if a field has no source value, omit it in the UI or show it as "No especificado"; preserve technical-sheet terms literally even if their meaning is unclear. Confidence: 0.8
- Design must be coherent with the existing design system — respect existing colors, typography, borders, shadows; avoid strident colors, unnecessary animations, or decorative clutter. Confidence: 0.75
- Requires explicit responsive behavior: balanced multi-column grid on desktop, single column on mobile, with no overflow, truncated text, or excessive empty space; images use `object-fit: contain` to avoid cropping/distortion. Confidence: 0.7
- Gives the product photo prominence: clean, modern, professional presentation with compact, well-spaced spec grids or lists. Explicitly objects to shrinking images ("no lo achiques, que se vea") — the product shot must be clearly visible and dominant. Confidence: 0.75
- When there is a tradeoff between image size and card size, enlarge the image and keep the card as compact as possible: bigger picture, same/looser card footprint. Confidence: 0.7
- Product images must blend into the card's background: no contrasting light/dark rectangle behind the photo. Since the PNGs are transparent, drop the image-stage panel; for images with their own background, use a blend (e.g. `mix-blend-mode`) so it matches the card color. Confidence: 0.75
- Wants spec lists curated for the audience, not exhaustive: put the most important / most attractive specs first and cap them at roughly the top 4, instead of listing every technical field — when trimming, any feature he names as a must-keep ("que se quede sí o sí") must survive. Confidence: 0.8
- Wants medium-sized, well-proportioned cards: featured image roughly 40–50 % of the card's visual height, uniform card widths/heights and alignment, moderate gaps between cards; explicitly rejects giant cards, tiny images, cramped text and excessive empty space. Confidence: 0.7
- Prefers compact horizontal cards over tall vertical ones: image on the left, information on the right, small enough that two cards fit side by side per row with the remaining one below (three cards → 2 + 1). Confidence: 0.8
- Wants filler copy removed: no generic marketing intro paragraphs, no repeated taglines or "incluido en el kit" banners — only the real description and the specs. Often says "borra eso" about any reusable-sounding sentence left in the UI. Confidence: 0.75
- When he flags something as redundant, expects it to be deleted completely from the page (section removed, dangling anchors fixed), not merely hidden or left unused. Confidence: 0.6
- When an image lives outside the project (e.g. a named file in `Downloads` / "que está en descargar"), expects the agent to find it, copy it into the project's real public assets folder for that feature, and reference it from there by a project-relative path — without moving or deleting the original. Confidence: 0.75
- Expects provided copy to be used literally: exact titles, labels and descriptions as written in the brief, not paraphrased or reworded. Confidence: 0.65
- Communicates in Spanish (informal, often with typos and run-on sentences) and expects Spanish responses and explanations. Confidence: 0.8
- Never fabricates functionality: no invented backend endpoints, no fake links, and no UI that pretends a not-yet-implemented flow already works («No inventes un endpoint de backend ni conectes una API inexistente. No muestres un enlace falso ni simules que el registro… ya funciona»). Confidence: 0.85
- When a feature's real flow/backend is not ready yet, expects a phased, honest approach: prepare a clearly-identified placeholder route following the project's routing conventions, with a page that states plainly the feature is not yet available and points to a real contact channel (e.g. the existing WhatsApp of the organizing team), leaving the real integration for a next stage. He chooses this honest option even when a working-but-different flow exists (e.g. preferred a disabled-submit group form over a working individual form). Confidence: 0.8
- For integration/feature tasks, wants a strict diagnostic-first gate: before modifying any code, inspect the real files and configuration, then deliver a brief diagnosis (files to modify, endpoints to use, env vars needed, possible blockers) and explicitly wait for his approval before implementing anything. Confidence: 0.9
- Treats repository boundaries as hard rules: when working on the frontend (`ciisic-undc-web`), never modify the sibling backend repo (`backend-ciisic`), never change the database schema or run migrations — new backend endpoints must be born in the backend's own spec/contract first. Confidence: 0.85
- Never expose secrets or introduce credentials into code; env tokens (e.g. `NUXT_BACKEND_EVENT_TOKEN`) must stay server-side and be verified absent from build output (`.output`) before delivery. Confidence: 0.85
- Never mark an inscription or payment as confirmed without real backend confirmation — no optimistic success states for flows the backend hasn't accepted. Confidence: 0.8

Confidence: 0.8

Confidence: 0.75

Confidence: 0.75
